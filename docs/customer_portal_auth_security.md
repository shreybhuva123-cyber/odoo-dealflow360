**Standard:** OWASP API Security Top 10 Compliant (API1:2023 Broken Object Level Authorization mitigation)

## Executive Summary & Hackathon Recommendation

In B2B deal flow platforms, the customer authentication system must be **strictly air-gapped** from internal employee access (Sales Agents, Managers, Finance Directors). Internal users authenticate into the Odoo administrative backend via standard Odoo ERP credentials (`base.group_user`). External customers authenticate through a dedicated, isolated customer gateway into the portal with external partner privileges (`base.group_portal` / `share=True`).

### 🎯 Recommended Approach for the Hackathon:
**Stateless Signed JWT with Partner Boundary Guard + One-Click Magic Link Invites**

#### Why this is the simplest secure approach:
1. **Zero Session Database Overhead:** No distributed session store (Redis) required.
2. **Built-in IDOR Defense:** Every JWT embeds `partner_id` and `commercial_partner_id`. A single 3-line Python decorator on backend controllers validates quote ownership with zero risk of cross-tenant exposure.
3. **Frictionless Demo Experience:** Magic-link tokens allow judges/customers to click an invite link in an email and immediately land in an authenticated quote review view without undergoing cumbersome registration flows.

## 1. Authentication System Architecture

```
[ Customer Browser / SPA ]
         │
         ├── (1) Credentials / Magic Link
         ▼
[ /api/v1/portal/auth/login ] (Customer Auth Controller)
         │
         ├── Validates credentials against external portal users (`share=True`)
         ├── Rejects internal employees attempting portal bypass
         ├── Encodes `partner_id` and `commercial_partner_id` into JWT
         ▼
[ Returns Signed JWT ] (HS256 with 60-min expiry + customer profile)
         │
         ├── Header: `Authorization: Bearer <token>`
         ▼
[ Protected Quote API: /quotes/{quote_id} ]
         │
         ├── Middleware extracts token claims
         ├── Queries DB: `quote.commercial_partner_id == token.commercial_partner_id`
         │     ├── MATCH -> Returns quote payload (with internal margins redacted)
         │     └── MISMATCH / NOT FOUND -> Returns 404 Not Found (Masking ID existence)
```

## 2. Customer Identity & Signup Model

### 2.1 Why Open Self-Signup is Disallowed in B2B Deal Flow
In an enterprise deal-closing platform, random public users cannot sign up without an existing commercial opportunity. Quotes are confidential commercial documents generated by an account executive for a specific enterprise legal entity (`res.partner`).

### 2.2 The Two Authorized Identity Onboarding Paths:

#### Path A: Deal Invitation Link (Invite-Only / Magic Link) — *Primary Hackathon Flow*
1. Sales rep creates a quotation for `Cyberdyne Defense Systems` and clicks "Send to Portal".
2. Backend generates a cryptographically signed HMAC invitation token containing `partner_id`, `quote_id`, and a 7-day expiration timestamp.
3. An invitation email is dispatched to the client:
   `https://portal.dealflow360.com/#/auth/magic?token=eyJhbGciOi...`
4. When the customer clicks the link, the portal frontend submits the token to `POST /api/v1/portal/auth/magic-verify`.
5. Backend verifies the signature, activates the portal user if first time, and returns an active JWT session.

#### Path B: Email & Password Authentication
1. Once activated, customers set an optional password for ongoing access.
2. Login authenticates via `POST /api/v1/portal/auth/login`.

## 3. Token & Session Structure

### 3.1 Token Format: JSON Web Token (JWT - RFC 7519)
- **Algorithm:** `HS256` (HMAC with SHA-256) using a 256-bit secret key `PORTAL_JWT_SECRET` (configured via environment variable, never committed).
- **Lifespan:** 60 minutes for active session access.

### 3.2 Token Header:
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

### 3.3 Token Payload Claims:
```json
{
  "sub": "usr_c91f0e4b81",
  "partner_id": 4821,
  "commercial_partner_id": 1205,
  "email": "sarah.connor@cyberdyne-defense.com",
  "company_name": "Cyberdyne Defense Systems",
  "can_sign_quotes": true,
  "role": "portal_customer",
  "iss": "dealflow360-auth",
  "aud": "dealflow360-portal",
  "iat": 1788605100,
  "exp": 1788608700
}
```

### 3.4 Key Security Attributes in Payload:
- `partner_id` (4821): Unique ID of the specific contact person (Sarah Connor).
- `commercial_partner_id` (1205): The parent enterprise company account. Enables multi-user corporate collaboration: Sarah Connor and her CFO John Smith can both review their company's quote because they share `commercial_partner_id: 1205`.
- `can_sign_quotes` (true/false): Explicit signatory flag preventing unauthorized junior team members from executing legally binding contracts.
- `role` (`portal_customer`): Ensures portal tokens can never be used against internal Odoo backend endpoints.

## 4. Complete Authentication & Session Lifecycles

### 4.1 Login Flow
1. User enters email and password into Screen 1 (`/portal/login`).
2. Client sends `POST /api/v1/portal/auth/login`.
3. Backend retrieves user record:
   - Must match email.
   - Must have `active: true`.
   - Must have `share: true` (verifies external portal customer, not internal staff).
4. Password verified against PBKDF2-SHA512 hash.
5. If valid, backend generates JWT and returns `200 OK` with user profile.

### 4.2 Magic Link Flow (Optional Passwordless Approach)
1. User enters corporate email and clicks "Send Magic Link", or receives invitation from sales rep.
2. Backend generates signed token: `HMAC_SHA256(email + partner_id + exp + secret)`.
3. Email sent with unique link containing `?token=...`.
4. Client opens link; frontend automatically calls `POST /api/v1/portal/auth/magic-verify`.
5. Backend verifies signature and expiration (< 15 mins for login links, 7 days for initial quote invites).
6. Backend returns standard JWT session.

### 4.3 Session Expiration & Refresh
- Access token expires in 60 minutes (`exp` claim).
- Frontend Axios/Fetch interceptor catches `401 Unauthorized`.
- If expired, interceptor attempts silent token refresh via `POST /auth/refresh`.
- If refresh fails, user is redirected to `/portal/login?redirect_to=...`.

### 4.4 Logout Flow
1. User clicks "Sign Out" in the portal navigation bar.
2. Frontend immediately purges the JWT from `localStorage` and client memory.
3. Client fires `POST /api/v1/portal/auth/logout`.
4. Frontend redirects to `/portal/login`.

## 5. Critical Security Requirement: Customer A vs Customer B Isolation (Anti-IDOR)

### 5.1 The Threat: Insecure Direct Object Reference (IDOR)
In poorly designed systems:
- Customer A (`Acme Corp`, `commercial_partner_id: 1001`) receives quote `QUO-2026-0001`.
- Customer B (`Stark Industries`, `commercial_partner_id: 2002`) receives quote `QUO-2026-0002`.
- Customer A opens browser DevTools, changes the request from `GET /api/v1/portal/quotes/QUO-2026-0001` to `GET /api/v1/portal/quotes/QUO-2026-0002`, and steals Customer B's confidential pricing and intellectual property.

### 5.2 The 3-Tier Zero-Trust Defense in DealFlow360:

#### Tier 1: Client-Side Routing Isolation
The frontend single-page app never allows navigation to a quote not present in the user's fetched list. If a user manually alters the browser URL hash to `#/quotes/QUO-2026-0002`:
- The frontend issues `GET /api/v1/portal/quotes/QUO-2026-0002`.
- When the backend rejects the request, the frontend renders Screen 13 (`Access Denied / 403`) or Screen 12 (`Not Found`), clearing all DOM traces of the requested resource.

#### Tier 2: Controller Ownership Guard (Backend Enforcement)
The controller **NEVER queries by `quote_id` alone**. Every query forces a dual-condition lookup:
```python
# SECURE PATTERN:
quote = (
    request.env["dealflow.quote"]
    .sudo()
    .search(
        [
            ("id", "=", requested_quote_id),
            ("commercial_partner_id", "=", token["commercial_partner_id"]),
            ("state", "in", ["sent", "in_negotiation", "approved", "expired"]),
        ],
        limit=1,
    )
)

if not quote:
  # Return 404, NOT 403!
  return json_error(
      404, "QUOTE_NOT_FOUND", "Quotation does not exist or has expired."
  )
```

#### Tier 3: 404-Masking Rule (Information Disclosure Prevention)
- If Customer A attempts to access Customer B's quote, the backend responds with **`404 Not Found`**, **NOT `403 Forbidden`**.
- **Security Rationale:** Returning `403 Forbidden` confirms to an attacker that Quote #0002 exists in the database. Returning `404 Not Found` completely masks the existence of other customer records, thwarting automated ID enumeration attacks.

## 7. Attack Scenarios & Defense Mitigations

| # | Attack Scenario | Attacker Action | DealFlow360 Defense | Result |
|---|---|---|---|---|
| 1 | **IDOR Parameter Tampering** | Customer A edits `quote_id` in URL or JSON body to inspect Customer B's quote. | SQL query enforces `commercial_partner_id == token.commercial_partner_id`. | Blocked. Returns `404 Not Found`. |
| 2 | **Token Forgery** | Attacker crafts a JWT with modified `commercial_partner_id` claim. | Backend verifies HMAC-SHA256 signature against server `PORTAL_JWT_SECRET`. | Blocked. Signature verification fails -> `401 Unauthorized`. |
| 3 | **Employee Bypass** | Disgruntled sales rep uses internal ERP login on Customer Portal. | Auth check verifies `share == True`. Internal staff accounts are denied portal tokens. | Blocked. Returns `403 Forbidden (EMPLOYEE_PORTAL_BYPASS)`. |
| 4 | **Signatory Impersonation** | Non-signatory team member submits `POST /accept` with fake signature. | Backend checks `user.can_sign_quotes`. If `false`, request is rejected. | Blocked. Returns `403 Forbidden (FORBIDDEN_SIGNATORY_REQUIRED)`. |
| 5 | **Replay Attack on Acceptance** | Network intercept resends `POST /accept` multiple times. | Backend enforces `Idempotency-Key` header and state guard (`state == 'sent'`). | Blocked. Cached confirmation returned; no duplicate orders created. |
| 6 | **Brute Force Credential Attack** | Automated script sprays passwords against `/auth/login`. | IP and Email rate-limiting (max 5 failed attempts per 10 minutes). | Blocked. Returns `429 Too Many Requests`. |
| 7 | **Expired Magic Link Reuse** | Attacker intercepts a 3-week-old magic link from an email. | Token payload embeds expiration timestamp (`exp`). | Blocked. Returns `401 Unauthorized (LINK_EXPIRED)`. |
